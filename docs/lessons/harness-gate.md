# Harness and gate evidence

## Context

A WPT reftest compares two documents rendered by the same engine. A matching pair can still share a defect. Harness summaries also compare runs with their selected filters, so aggregate deltas can mislead.

## Durable practices

- Compare reports by exact test ID. Confirm that both reports use the same selection, source revision, WPT revision, engine binary, page settings, and fonts.
- Render the test and reference separately when a status flip, page count, or pixel result is surprising. Inspect the fixture text and both inputs before classifying a flip as a regression.
- Treat a PASS as pair equality only. Use direct checks for page count, geometry, text, orientation, paint, and links when the capability can change both sides together.
- Measure both page counts. A mismatch message does not establish which side is correct. Match the harness page specification, including page size and margins, in standalone reproductions.
- Use browser results and CSS specifications as comparison evidence. Confirm browser page-size preferences and other print settings before comparing output.
- Use fresh binaries built from the exact revisions under comparison. Keep baseline reports and raw evidence outside worktrees that may be removed.
- Check the reference before blaming the test. A reference that depends on an unsupported layout feature can make a valid test impossible to match.
- Inspect PDF content streams before changing layout code for small pixel differences. Rasterization can explain a difference after geometry already matches.
- Use exact test identifiers. A substring filter can select a different or additional test.
- Do not pipe test commands through a status-masking filter. Save output and check the command's exit status.

## Lessons

Probe scripts named below (`probe-render.py`, `oracle-mb.py`, `page-counts.py`, `render-inventory.py`, `diff-reports.py`) are skill assets, not repo files — copy them out of the `typeanvil-issue-loop` skill into `<worktree>/probe/` before running them.

- **A saturated background MASKS its own text in the ink map** (verified): a cell over a green margin box classifies as the COLOUR (saturated colour outranks grey), so "one line" and "two lines" look identical and the only visible signal is a ~20-pixel difference in the colour's own pixel count. To decide a line question, render the fixture and count DARK pixels per pixel-row inside the box rect (a `rows.py`-style probe), not the colour map.
- **The harness run summary's `pass-rate delta vs run #N` and `newly broken` compare against the PREVIOUS RUN whatever filter it used** (verified): a 37-test bucket run printed "newly broken: 148" and "+29.2% vs run #12" purely because run #12 was a full 283-test run. Evidence is a per-test-id diff of the two report JSONs, never the summary line.
- **A flip can be an EXPOSED ACCIDENTAL PASS — measure each SIDE at baseline AND candidate** (verified): `css-page/fixedpos-004-print` went PASS→FAIL and the aggregate said nothing useful. Rendering each side separately with BOTH binaries showed baseline had test=1 page AND ref=1 page: it only passed because both sides were wrong the SAME way, while the fixture's own text says "There should be three pages". The change fixed the REF side (now the intended 3 pages) and left the test side's pre-existing gap exposed. Before calling a flip a regression, line up three facts: which side moved; what the fixture/ref INTENDS (read both files); and browser ground truth (next bullet). Standing user ruling: land the spec-correct change and record the flip as an EXPOSED GAP — never revert to re-match two wrongs.
- **wpt.fyi ground truth costs two calls** (verified): `GET https://wpt.fyi/api/runs?products=chrome&labels=master&max-count=1&aligned=true` returns the newest run with a `results_url` pointing at a `...-summary_v2.json.gz` (plain JSON despite the extension). Download it and index by test PATH: `d['/css/css-page/fixedpos-004-print.html']` → `{'s': 'P', 'c': [0, 0]}` (`P`/`F`/`E`). Use it to decide whether a fixture is VALID before believing our behaviour is wrong — and to justify an accidental-pass flip as an exposed gap rather than a regression.
- **Compare gate reports PER TEST, and keep the baseline report where you can still read it** (verified): identical totals (150/133) hide a one-up-one-down swap. Diff the two report JSONs by test id. Write the baseline report OUTSIDE the worktree you are about to delete — a report written to `/work/gate-*.json` dies with the worktree, which forces an expensive rebuild of the baseline when the totals turn out to need looking at.
- **Check the PDF content streams before chasing the last few pixels** (verified): 50 differing pixels in one column looked like a layout rounding bug. Both sides placed the box at exactly `85.37695`pt — read out of the streams (`85.37695 0 m ... h f` on one side, `75 0 0 37.5 85.37695 178.5 cm /x0 Do` on the other). The difference was the RASTERISER rounding a raster image's edge outward while rounding a vector fill to the nearest pixel. When a fixture compares an image against a simulated image (a background colour), no layout fix can make them match, and a rasteriser-target snap is not the engine's call. Dump the streams (inflate with zlib, split on whitespace, read the tokens before `Do` / `re` / `l ... f`) before spending a cycle on probes.
- **The harness Chromium oracle does NOT paint margin-box `url()` background images** (verified, 2026-09-14): `@top-center { background: url(/images/green.png) }` renders ZERO saturated pixels via the harness oracle while `background: lime` (colour) paints a full-width band — yet wpt.fyi Chrome PASSES `background-001`. For margin-box background-image fixtures, ground truth is wpt.fyi plus the ref fixture, NOT the harness oracle (which also cannot run twice in one process: the playwright sync API breaks on the second `ChromiumEngine` render — render one fixture per process).
- **The harness Chromium oracle is NOT ground truth for test-vs-ref parity in `css-page/margin-boxes`** (verified): in Chromium via the harness, `dimensions-003`'s test paints a 92x62 yellow box while its own reference paints 72x62, and `auto-margins-002` gives 474x282 against 328x288. A validated WPT test must match its reference in the validating browser, so the harness's Chromium settings do not reproduce WPT's conditions for this bucket. Do not settle a spec question from its test-vs-ref deltas, and do not add an "adapter" to normalise them (the harness owns `harness/engine.py`; changing it to suit one bucket risks 283 unrelated tests). It IS decisive for a SINGLE document's absolute behaviour — it settled a spec question here (Chromium paints a declared-height inline-block in full from the page top) and it showed Chromium keeps the page at 5x3in rather than growing it for `@page { width; height }`.
- **Probe pixels, not text: our PDFs are glyph-only** (verified): `pypdfium2` `count_chars()` returns 0 for engine output, so a text-extraction probe reports "no text" even when ink is on the page. Use `scripts/probe-render.py` (renders any HTML with the CLI, then prints saturated-colour region bboxes plus an ASCII ink map computed over every pixel) — an 80x26 map makes geometry deltas obvious at a glance and beats vision at 96 DPI. `scripts/oracle-mb.py` does the same for Chromium via the harness's `ChromiumEngine`, but playwright's browsers are NOT installed in the dev image (`BrowserType.launch: Executable doesn't exist at /home/dev/.cache/ms-playwright/...`) — install once into a mounted path (`PLAYWRIGHT_BROWSERS_PATH=/work/.pw-browsers playwright install chromium`) or run the oracle on the host.
- **Classify PASS→FAIL flips by rendering the REF separately with declared-height arithmetic** (verified): when the ref declares `height:<N>vh` and starts rendering its correct page count after a height fix, the flip is a ref-side correction — the test side's residual is a DIFFERENT missing feature (abspos plus `contain:size`), not a regression. Probe per-page text and pixel profiles of test AND ref on both binaries before counting any flip against a change.
- **Stale WPT baselines fake regressions** (verified, 2026-08-24): the committed `wptreport.json` can predate the harness's current bucket set, so a naive diff flags PASS→FAIL "regressions" that are actually baseline drift. Before believing any regression count, re-run each flagged test on BOTH binaries today; only identical-input status flips count. Also compare on the intersection of test ids when one report has tests the other lacks.
- **Browser ground truth for a failing WPT test: cross-reference wpt.fyi master runs** (verified, 2026-09-14): `GET https://wpt.fyi/api/runs?products=chrome,firefox,safari&labels=master&max-count=1&aligned=true` → each run has `results_url` (summary_v2 JSON, NOT gzipped despite the `.gz` name). Format: `{test: {"s": status, "c": [passed,total]}}`; `s`: P=pass, F=fail, O=OK-with-subtests (pass iff `c[0]==c[1]`), S/N=skip. Test keys are `/css/css-page/<file>` — prefix our ids with `/`. Firefox fails print-reftests wholesale (122/283 of ours) because it does not support them — its fail is NOT evidence a test is bad. **Chrome is the only real oracle for print-reftests.** Of our 283 targets (test revision `f2d99507a2`, 2026-09-14): Chrome fails 29 (20 we fail → invalid-test/spec-ambiguity candidates; 9 we pass → accidental-pass suspects); the rest are real engine gaps when we fail.
- **The worktree's harness `.wpt` symlink must point at MAIN's checkout, and `--cli-cmd` must be ABSOLUTE** (verified, 2026-09-07): the harness resolves `.wpt` relative to `harness/` (so symlink `harness/.wpt -> <checkout>/.wpt`, NOT `<checkout>/.wpt` which does not exist under `harness/`), and `$PWD` inside `--cli-cmd "$PWD/target/..."` expands to the harness dir when run from there — every test ERRORs with `FileNotFoundError`. Use the full path.
- **`--cli-cmd` must include the `render` subcommand** (verified, 2026-09-10): `--cli-cmd "<path>/engine/target/debug/typeanvil render"` — omitting `render` makes the CLI reject the input path as an unknown subcommand and the ENTIRE 283-test run comes back ERROR in ~10 min (wasted gate). If a full run finishes suspiciously fast with all-ERROR, check this first. Put the full invocation VERBATIM in any worker prompt (workers repeat the parent's mistakes; one worker died budget-less on this).
- **Accidental passes must be judged, not preserved** (verified, user-approved): a vh/vw fix flipped `fixedpos-007/008` and `underflow-from-next-page` PASS→FAIL — all three declare vh and had passed only because the fixed 1024x768 viewport put content where the ref happened to match. With the user's OK, landed the spec-correct change (net +4) and documented the 3 flips as newly-exposed engine gaps (abspos-across-pages, negative-margin-at-breaks). Probe each regression test's SOURCE for the changed property before treating a flip as real; if it declares the changed unit/property, check whether its old pass was accidental, then ask the user when the zero-regression rule and `docs/conventions/css-standards-alignment.md` point opposite ways.
- **A feature can be correct with zero WPT flips — land it anyway when the gate is clean** (verified, 2026-09-11): Ahem font loading and @page counters produced zero status changes because the target refs' residuals live in OTHER features (grid layout, margin-box sizing). Verify the capability directly — text extraction vs ref values, embedded PostScript name in the PDF — and record per-target value tables; the seam is then proven for whatever fix unblocks the refs later.
- **A reftest can pass with symmetric missing features — probe BOTH sides before adding scope** (verified): `page-margin-007`'s `::before` text renders on NEITHER side (stylo `match_pseudo_element` returns false unconditionally), so it cancels in self-consistency. The test passed at 0 px diff without implementing `::before`. When a test and ref both lack the same feature, document it as a residual instead of expanding the fix.
- **Composition beats single-feature thinking** (verified, 2026-09-11): the grid stretch (`align-content` normal → stretch auto rows of a definite-height container, css-grid-1 §12.8) landed 8 FAIL→PASS in one gate — but only because the earlier vh resolution work (a different issue) had landed earlier. When a feature shows zero flips, check whether the OTHER half of the composition is missing before concluding it is useless; and re-test older "zero-flip" features after each new enabling fix.
- **WPT ref files simulate engine output with whatever CSS is convenient** (verified): refs used grid-at-100vh wrappers and flexbox auto-margin centering to simulate named-page geometry. A failing test may mean the ENGINE lacks the ref's simulation features (grid stretch, flex auto margins), not that the tested feature is wrong. Diagnose the ref's markup the same way as the test's.
- **Paint-symmetry regressions need a canary check BEFORE building** (verified): `page-box-000` passes only because NEITHER the test's @page border NOR the ref's html-root border paints. Implementing either side alone flips the canary PASS→FAIL (11818 px). Probe what the CANARY ref relies on before landing any new paint feature; if the ref depends on a missing feature, that feature must land FIRST (html-root-box).
- **WPT ref files simulate the TEST's features with whatever CSS is convenient — when the ref uses a feature we lack, the TEST can never pass** (verified): `page-left-right-002` needs `direction:rtl`; `page-margin-007`'s page-filler divs need declared-height pagination. Check the REF fixture's markup for unsupported features BEFORE implementing the tested feature.
- **The harness Chromium oracle passes `prefer_css_page_size=False`** (verified, 2026-09-13): every oracle page count is at the harness's 5x3in page, NOT the fixture's declared `@page size`. For fixtures that declare a size (`page-box-008/009`'s 400x800px), oracle page counts are about the 5x3in render only — the fixture-as-designed geometry must be probed with the ENGINE's render (which honors @page size) against the ref's border simulation, and the Chromium test-vs-ref deltas for such fixtures are doubly unreliable (shrunk-to-fit plus wrong page size).
- **`--filter` is a SUBSTRING — read `results[0]` per report, not per filter** (verified, 2026-09-14): `--filter page-margin-auto` matches BOTH `page-margin-auto` and `page-margin-auto-and-non-zero`; `d['results'][0]` is the FIRST (alphabetical) = `auto-and-non-zero`. I "confirmed" `page-margin-auto` passing 6/6 when it was the OTHER fixture. Always match the exact test id from the report (or re-filter with a tighter string) before declaring a target green.
- **Accidental passes and invalid-test flips are dispositioned through the sweep buckets** (verified, 2026-09-14): `layers-003` and `page-name-margin-001` flipped PASS→FAIL from the body-margin fix — both are invalid-test candidates (Chrome AND Firefox fail them), so the flips EXPOSE test bugs. And `page-box-003`'s PASS is an accidental-pass suspect (we pass, Chrome fails) — annotate it, do not count it as conformance. When closing an issue, disposition EVERY residual through the sweep buckets (`docs/research/wpt-harness/wpt-ground-truth-sweep-2026-09.md`) instead of stretching the issue across unrelated features.
- **pypdfium2 render arrays are BGR in this environment** (verified): a probe reading (255,0,0) is BLUE, not red. Sanitize colour names before reasoning, or channel-order confusion will invert an entire diagnosis (this cost an hour on `page-box-002`).
- **Gate baselines must be FRESH builds of the exact branch-point commit** (verified, 2026-09-04): a release-worktree binary can be stale relative to origin (other sessions push between builds), and other sessions' squash-lands move the branch point under you. The first gate flagged `monolithic-overflow-007/008` as regressions; re-gating against a freshly-built branch-point binary showed they were already broken there (a grid plus monolithic-child issue), not regressions from this change. Before believing ANY flip: `git log --oneline -1` the base worktree, rebuild its binary, and confirm the commit equals your branch point.
- **Harness runs must happen INSIDE the dev container** (verified): the `harness` module is not pip-installed — run `PYTHONPATH=/work python3 -m harness` with cwd `/work/harness`, and `--wpt /main/.wpt` (main mounted read-only at `/main`). A host-side run pointing `--cli-cmd` at a worktree path whose `engine/target` lives in a Docker volume yields all-283-ERROR in seconds (`FileNotFoundError`). Write `--report` to `/work/...` (a mounted worktree path) — `/tmp` is container-ephemeral and `/io` does not exist. Full 283-test run ≈ 5–8 min inside the container.
- **A WPT PASS can be two wrongs matching** (verified, 2026-09-04): `fixedpos-009` passed only because test AND ref rendered wrong identically (both engines mis-placed the pencil; the fixed side was pinned to page 1 and the ref's abspos pencils did not repeat either). Fixing one side flips PASS→FAIL even though that side got MORE correct. Before treating any flip as a regression: render test and ref separately with a pixel/charbox probe and compare WHERE each side differs; check wpt.fyi for browser ground truth. Document the residual honestly instead of re-breaking the fix. Also: pre-existing test failures that "do not respond" to a fix may share a root cause with the ref side, not the test side.
- **Standalone repros must match the harness PageSpec** (verified): the harness renders WPT print-reftests at 5×3in WITH 0.5in margins on all sides. A manual render without the margins can differ (a multicol flip reproduced only with margins). Check `engine.py` PageSpec before declaring "cannot reproduce".
- **The WPT gate is SELF-CONSISTENT, so it cannot see a UNIFORM change** (verified, 2026-09-15): the harness compares OUR test render against OUR reference render through the SAME engine, so a change applied uniformly to BOTH sides of a pair leaves the pair matching. A re-key that regressed the Chromium-verified page count of `page-name-orthogonal-writing-003` (1 → 2 pages) produced **ZERO flips**, with both 283-test reports identical per test id. `engine/tests/` is the guard of record for pagination in this bucket, so ALWAYS run the full suite (green: 372 tests / 42 binaries). Read a clean A/B as "the pair still matches" only. The whole loop is cheap: one changed file rebuilds in ~6s and a full 283-test run takes ~90s in-container, so iterate empirically instead of reasoning about layout geometry.
- **The harness Chromium oracle RUNS ON THE HOST** (verified, 2026-09-15): `<checkout>/.venv/bin/python` has playwright plus chromium installed, while the dev image has no browsers at all. Drive `harness.engine.ChromiumEngine` from the MAIN checkout with that venv python, one render per process. Two decisive moves it enables: count per-page ink with pypdfium2, and read the TEXT layer with `page.get_textpage().get_text_range()`. A Chromium PDF carries a real text layer, so "does the browser paint the element's own text or its generated image?" is answerable directly — this read an EMPTY text layer on every page, which proved Chromium applies element `content: url()` rather than falling back to the element's text.
- **Piping `cargo test` through `grep`/`tail` MASKS its exit code** (verified): the pipeline reports the filter's status, so a run can look green while a binary failed. Redirect to a file and read the real code — `cargo test ... > /work/test-out.txt 2>&1; echo "cargo exit=$?"; grep -c "test result: ok" /work/test-out.txt; grep -c "test result: FAILED" /work/test-out.txt` — the suite is 42 binaries, so expect 42 result lines.
- **A ticket's stated root cause is a HYPOTHESIS — disprove it against the fixtures before writing code** (verified, 2026-09-15): a ticket blamed "per-side border colours" for `paint-order-001/002`, but those fixtures declare only `border: solid thin`; the real blocker was paint order/`z-index`, and `grep -rl 'border-(top|right|bottom|left)-color'` over the whole bucket returned ZERO fixtures. Three cheap checks settle it: grep the NAMED fixtures for the property the ticket blames, read the harness message (a page-count mismatch and a pixel diff are different bugs), and check wpt.fyi for the fixture's validity. When the blamed property appears in no target fixture, the ticket is mis-scoped: take the re-scope to the user (they chose it) and file the disproven-but-real bug as its own issue rather than silently dropping it.
- **Probe the REFERENCE before blaming your own side, and read the DIFF SIZE as a signal** (verified): a diff covering 63% of the page is a LAYOUT failure, not a paint-order near-miss. Rendering the fixture's ref through our own engine and reporting per-colour pixel counts plus bounding boxes (`probe/regions.py`) showed `paint-order-001`'s ref paints NO pink and NO yellow box at all — its grid/flex plus inline `z-index` simulation does not lay out, so no amount of test-side correctness can match it. That finding turned an unbounded "fix the fixture" job into a clean, bounded one (`003` passed; `001/002` filed as a ref-side issue).

## Verification

The current harness entry point is `python3 -m harness`; its `run` command writes the report path supplied by `--report`. The CLI engine command must include `render`, for example:

```bash
python3 -m harness --wpt /path/to/.wpt run \
  --engine cli \
  --cli-cmd '/path/to/typeanvil render' \
  --filter 'css-page/margin-boxes/content-003-print.html' \
  --workers 1 --report /tmp/report.json --db /tmp/history.sqlite
```

Use the repository's container runbook when the engine binary or Python dependencies require the container. A completed reproduction is evidence about that input; it is not a gate pass.
