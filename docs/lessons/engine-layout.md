# Engine Layout: Flex, Grid, Margin Boxes, Writing Modes

Layout lessons verified against real CORE issues. Read this before diagnosing any flex, grid, margin-box, paint-order, writing-mode, or measurement problem in the engine.

## Lessons

- **A box that "places nothing" but breaks inside must defer with `break_before_deferred()`, not a plain `break_before()`** (verified CORE-235, 2026-09-21): the CORE-167 deferral and the `placed_nothing` deferral in `layout.rs` both emitted a plain `break_before()` token, dropping the `deferred_once` flag. A child whose declared extent equals a full page but sits inside table chrome (border+padding+border-spacing leaves less than a page) can NEVER fit, so it re-deferred fresh on every page and the table emitted an identical continuation forever — `table-fragmentation-003a/b` ran away to 100000 pages. Fix: emit `break_before_deferred()` and guard the deferral on `!child_tok.deferred_once`, so a box that STILL cannot fit the next page force-places instead of deferring again (mirrors the row-deferral pattern). Signature: a table that terminates at baseline but runs away after a separate-model change, with the same `y`/`height`/child-token on every continuation page. Also: a fresh row that broke inside must claim only its actual placed height (`used_h`), not the full measured `row_height` — over-claiming advances the table cursor past the break, makes the table think it finished, and paints its bottom chrome early (001a's table border box was 198pt vs the ref's 144pt).
- **A mode-switching wrapper is not automatically an orthogonal-flow context** (verified CORE-155): page-change suppression must compare the writing mode IN EFFECT at the page-declaring boxes against the PAGE's flow mode (the root element's `writing-mode`) by AXIS — vertical vs horizontal. The old predicate ("any intermediate ancestor-or-self declares `writing-mode`") suppressed the break in `page-name-orthogonal-writing-004`, where an `horizontal-tb` wrapper nested inside a `vertical-rl` one carries the page's OWN mode and the ref forces the same break with `break-after: page`. Hooks: `Ctx::writing_mode_at`, `Ctx::page_flow_writing_mode`, `orthogonal_flow` (engine/src/layout.rs); spec `docs/specifications/named-pages.spec.md` Behavior 4; tests `engine/tests/page_boundaries.rs`.
- **Adding a field to a public struct breaks struct LITERALS in tests** (verified CORE-174): `LineResult` gained `trailing_space` and `engine/tests/typography.rs` failed to compile with `missing field 'trailing_space' in initializer`. Before believing a compile error is environmental, grep `engine/tests/` for `<Struct> {`. Cheapest fix is to add the field with a zero value at each literal.
- **A line-baseline shift must move TEXT fragments only** (verified CORE-173): the first version of the tall-inline-block baseline fix shifted every child sitting on the line, which dragged a previously placed inline-block 3pt down with it. `inline_block.rs::two_inline_blocks_side_by_side` caught it ("both boxes share one line (equal y): got 39.039844 want 36.000000"). When you shift fragments already placed on a line, filter by content kind (`if let FragmentContent::Text(run) = &mut child.content`) and leave each atomic to manage its own placement.
- **Check the branch you patch is REACHABLE before believing a no-effect fix** (verified CORE-172): the bare-text loop in `layout.rs` guards its full-width branch on `!atomic_line_active`, but the flag is set to `true` a few lines ABOVE that condition, so the branch is dead and every text run takes the segmented (float-aware) path. Patching the dead branch built cleanly and changed nothing on the pixel probe. The signature is a fix that compiles and leaves the probe byte-identical: before editing a branch that guards on a flag, grep every write of that flag and check whether one dominates the test. Put the fix where the code actually runs, and record the dead branch on the issue rather than silently reconciling it.
- **A fragment-SIZE assertion can pass while the PAINT is wrong** (verified CORE-171): a `100x50` inline-block had a correctly-sized background fragment (75x37.5pt) that was shifted 23.6pt ABOVE the page top, so only a 13.9pt slice painted. The test passed; the bug was live. Assert the invariant that actually fails (a page-absolute position, `y >= 0`), and prove it fails pre-fix: `git stash push -- engine/src/layout.rs` (keep the test), run it, confirm the failure message names the wrong value, then `git stash pop`. Suspect the same shape whenever a box is the right size but the pixels are a slice: alignment shifts move whole subtrees, so a single clamped delta beats re-deriving the geometry.
- **§5.3.2.2: a lone/empty middle box takes the FULL edge, never half** (verified CORE-141, 2026-09-14): with side boxes absent (or empty), the imaginary AC pair has zero extents, and distribute_pair's "flex factors assumed 1" fallback splits the available width 50/50 with a box that does not exist — an empty `@top-center { content: "" }` rendered 132pt of a 264pt edge while Chrome paints the full band (background-001's ref expects full width). Fix in `margin_box::resolve_variable`: when `ac_max == 0`, hand the auto middle box the whole available width; keep distribute_pair when AC has content. The same fallback for the A/C pair (two real empty boxes) is correct — scope the change to the B-vs-AC pair.
- **Margin-box `line-height` and a trailing forced break both corrupted §5.3.2.2's measurement** (verified CORE-184, 2026-09-15): `MarginBoxStyle` had no `line-height` field and `apply_font_shorthand` discarded the `/1` in `@page { font: 16px/1 Ahem }` (`if let Some((sz, _lh))`), so every multi-line margin box measured at the `normal` 1.2em pitch; and `margin_box_lines` split on `\n` so `content: "x\ax\ax\a"` measured FOUR lines where the fixture states three. Both feed the block extent, which drives the proportional distribution of the whole edge — the symptom is not "text is misplaced" but "every box on the edge has the wrong size". Read the fixture's OWN commented arithmetic (these files state the expected em values) and compare it against an instrumented dump of the resolved boxes before touching layout code; the numbers are a free unit test.
- **`@page { width; height }` is the page AREA, and the page box must grow to area + margins** (verified CORE-141): the WPT `css-page/margin-boxes` fixtures are designed in pairs where the test's `@page { margin: 6em; width: 20em; height: 16em }` plus its margins equals the reference's declared page box (`@page { margin: 0; width: 32em; height: 28em }`). Clamping the declared area to the CLI 5x3in page makes the two sides render at different sizes, so nothing in the bucket can match. Per css-page-3 §3 an over-constrained area RESIZES the page box to the margin edges instead. **RE-VERIFIED 2026-09-15 (CORE-184) — the engine currently does the OPPOSITE and the spec codifies it.** `paged.rs` keeps the CLI page size and fits the declared area inside it, with a NOTE rejecting the growth; spec `paged-media-css.spec.md` Behaviour 6 states the area "shall NOT resize the page box" (CORE-144). Browser ground truth disagrees, measured directly (NOT via the harness oracle, whose `prefer_css_page_size=False` hides this): drive `playwright.chromium` on the host with `prefer_css_page_size=True` and read the PDF page box with pypdfium2 — `dimensions-005-print.html` (`margin: 6em; width: 20em; height: 15em`) and its ref (`width: 32em; height: 27em; margin: 0`) BOTH come out 384x324pt, and `page-size-015-print-ref.html` (`width: 7.5in; height: 6in`) comes out exactly 7.5x6in. `page-size-015-print.tentative.html` says it in words: "The page size should be 7.5 by 6 inches" for `width: 150vw; height: 200vh`, with `vw`/`vh` resolved against the DEFAULT page box. So: a declared `@page { width; height }` sets the page box to area + margins and overrides `size`. Treat a measured "Chromium keeps the requested size" claim as an artifact of the oracle's `prefer_css_page_size=False` until re-measured with it True. Flipping this needs a spec edit + the user's ruling; measure how many of the `dimensions-*` family turn on it first — the Chrome-PASSING members (005/007/008/009/011/012) have no `writing-mode` in a margin box, while 013/014 do and are Chrome-FAILING (Chromium renders 013's test as 1 page and its ref as 2, so the pair cannot match at all).
- **A margin box's available extent is the page AREA, not the page box** (verified CORE-141): css-page-3 §5.3.1's "available width" reads as the page box, but Chromium and the bucket's references both size the three edge boxes to the page AREA's extent, with corner boxes taking the side margins. Read the fixture comments — `dimensions-*.html` states its arithmetic in em ("Available size for top edge margins is 20em", "Left width: 3em + 15em * 3/5 = 12em") and the numbers match §5.3.2.2 exactly, so they double as a free unit test (see `margin_box::tests`).
- **Margin-box refs simulate the boxes with grid/flex/abspos, so a fix only lands when BOTH sides work** (verified CORE-141): the test side needs the §5.3 box model (geometry + background/border paint + empty `content: ""` boxes still generating), while the ref fakes the same shapes with grid tracks, flex `stretch`/`shrink`, `overflow: clip` and abspos. Probe the ref alone first: if its coloured regions are missing or the wrong size, the test can never match and the work belongs to the ref-side feature instead.
- **A measure fix must keep the margin/padding pedestal ADDITIVE for auto boxes (verified CORE-176):** making declared extent compete with content is right (css-sizing-3 §4), but if the implementation makes content compete against the WHOLE pedestal (`h` starts as margins+padding), an auto box with `margin-bottom: 2em` and one line measures 2em, not 3em — short content silently vanishes from the measure and shifts abspos/anchor geometry (fixedpos-004 flipped PASS→FAIL ref-side only, 3546 px on one band). Structure it as: `content_h` stacks on the pedestal; the declared target (extent − padding + margins, in margin-box terms) competes with `content_h + pedestal`. Probe regressions by rendering test AND ref with probe-render.py on both binaries — a ref-side-only pixel shift in a pure block+abspos doc points straight at measure_block.
- **Separate page-change tests from border overflow.** A `height:1in` content-box with `2px` borders overflows a page with exactly `1in` content height. Chromium produces a short border continuation before the next named-page change, so three pages can be correct when an older test expects two. Use `box-sizing:border-box` to isolate the named-page invariant, and add separate content-box overflow coverage. Probe both variants before classifying the old assertion as a regression.
- **WPT flexbox 081/082 residual root cause (CORE-120):** refs bottom-align inline-blocks to the surrounding text baseline; engine v1 aligns box bottoms → one-line-pitch border shift. Charboxes are the reliable probe (test vs ref '1'/'2' x matched exactly post-fix).
- **Leader/TOC fill lands short of flush**: `floor(room / pitch)` discards up to one dot-pitch. The engine absorbs the residual via TextRun expansion (±2% clamp) at draw time — reuse that mechanism, don't touch the two-pass reservation model.
- **A hand-maintained const list used with `binary_search` MUST be sorted** (verified CORE-112): `"width"` listed before `"widows"` silently missed every `widows:` declaration ('o' < 't'). If the list is not covered by a test that probes a known-hit near the end alphabetically, sort-check it.
- `Scalar` has NO Ord/Hash by design — clamp with explicit `if a.get() > b.get()` comparisons, never `.min()/.max()`.
- **Test helpers reading `Fragment.offset` directly report PARENT-relative coords** (verified CORE-121): walking the fragment tree must accumulate offsets down the tree to get page-absolute positions. Also: pdfium charbox y is measured from the BOTTOM of the page, so a downward paint shift shows as a smaller y. And out-of-flow boxes paint AFTER in-flow ones, so `lines[0]` on a page with abspos content belongs to the in-flow text.
- **A forced-break penalty of -inf poisons the K-P demerit accumulator** (verified CORE-158/159, 2026-09-11): best[j] = -inf makes every downstream path tie at -inf and the adjacent-predecessor tiebreak degenerates to one-word-per-line lines after any `<br>`. Fix: enforce mandatory breaks STRUCTURALLY (prefix guard) and cost 0 demerit.
- **Percentage height needs a definite-extent walk, not a flag flip (verified CORE-169):** resolving `height: <pct>%` (css-sizing-3 §5.3) requires BOTH a new `resolved_height_or_percent` (walk ancestors for the nearest definite `specified_extent`, resolve against its content height) AND threading the node id into `specified_extent(id, style)` so every CORE-167 consumer (`remaining_spec` in layout_box, measure_block, the early-outs) sees the resolved value. Wiring only the resolver leaves the paint box at 0 (empty div with height:100% renders nothing) — `remaining_spec` is what grows the paint box.
- **Flex `cross_size` is margin-INCLUSIVE; stretch targets are margin-box math (verified CORE-153, 2026-09-12):** the flex measure path bakes margins into `cross_size`, so a stretch target computed as `line.cross - margins` compared against it silently no-ops (39 vs 59.4). Grow the item's `cross_size` to `line.cross` itself; the PAINT override handed to the block path must be `line.cross - margins`. Signature: WPT refs whose flex children are `flex:1; margin:30px` render at content height instead of filling the line.
- **Key flex-path maps by `block_index`, not enumerate index (verified CORE-153, 2026-09-12):** `collect_flex_items` preserves each item's position among the container's BLOCK children (that's what `child_tokens` resume is keyed on). A Phase-A map keyed by the flex-item enumerate index misses in placement when text items shift positions — symptom was page 1 of a ref not stretching while pages 2-6 did (resumed containers hit the `child_incoming` path, fresh ones didn't).
- **The @page logical margin/padding axis mapping ignored the page writing mode (verified CORE-153, 2026-09-13):** the @page parser folded `margin-inline-*`/`margin-block-*` (and padding counterparts) onto physical edges as horizontal-tb AT PARSE TIME. On a vertical-rl page context the edges came out backwards (measured left 8/right 24/top 64/bottom 160 vs the refs' border-simulated 80/32/16/48). Fix pattern: keep the logical longhands SYMBOLIC in PageRule and map them in `resolve_page_spec` against the page context's EFFECTIVE writing mode — the cascaded `@page { writing-mode }` else the ROOT element's computed mode (css-page-3 §3). TWO seams: (a) `@page { writing-mode }` was previously not parsed at all; (b) stylo's servo build does NOT compute writing-mode — `get_inherited_box().clone_writing_mode()` returns the initial (HorizontalTb) even for `html { writing-mode: vertical-rl }`, so read the root mode from the ENGINE's own cascade pass (PagedDecl::WritingMode must carry the parsed value, not just set the CORE-127 boolean). The percentage axis follows the mapped physical slot (top/bottom % → HEIGHT, left/right % → WIDTH), so no separate percentage logic is needed.
- **Vertical writing-mode block geometry (fixed 048b33a, CORE-153, 2026-09-14):** a block in a vertical writing mode fills its INLINE axis — auto height = the page content box (page-size-012's auto-height div = 550x400; the ref simulates it with `height: 400px`). And only vertical-RL right-anchors definite-width boxes with `margin-right` (page-margin-002's ref); vertical-LR runs left→right like LTR (page-margin-003's ref breaks if you right-anchor it — the `root_wm != HorizontalTb` test is too broad, use `== VerticalRl`).
- **Debug probes in release code: remove before landing** — grep for SPECDBG/BORDERDBG/RINGDBG/FLEXDBG/BOXDBG eprintln!s after diagnosis; the session that follows will not know they exist.
- **Block bg+border lost its border band: insert-then-overwrite (verified CORE-165):** the block path pushed the Border as `fragment.children.insert(0, bf)` but later `fragment.children = children;` overwrote it — any block with BOTH background and border silently lost the band (stylesheet borders on bg'd divs never painted; inline-only looked fine by accident). Fix: attach AFTER the `children` assignment. When touching fragment assembly, check what happens between insert and the final assignment.
- **Table cells double-band if the block path also attaches (verified CORE-165):** the block-path border attach must skip `Display::TableCell` — the table path owns cell borders (border-collapse aware). Caught by core119_cell_height (two Border fragments at the same x).
- **visibility is paint-only — never fold it into geometry (verified CORE-165):** `@page { visibility: hidden; border: ... }` must keep the border's content inset but skip the ring paint. Suppressing the border entirely shifts text and fails page-visibility-hidden-001.
- **`border: solid` (keyword width) = medium 3px (verified CORE-165):** both the element border pass and the @page parser must default the width to medium when a style keyword is present and no width was given; otherwise keyword-only borders silently don't paint/inset.
- **Scalar has no Ord — and a clamp with a NEGATIVE cap inverts (verified CORE-165):** `@page` margins taller than the page make content height negative; `min(v, half_h)` with half_h < 0 returns the NEGATIVE cap. Clamp v to ≥0 first, and cap to ≥0.
- **Segmented-path byte offsets must use the segment's ENTRY offset (verified CORE-146, 2026-09-07):** in the float-wrapped text path, `src_offset` advances per line inside the line loop AND seeds the next segment's re-break. Any window/byte math computed as `src_offset + Σconsumed[..li]` inside that loop double-counts the segment's placed lines (drift = exactly 2× true offset). Footnote call markers silently vanished for notes called after a segment's first line; two wrongs (note 1 dropped + note 2 mis-attached) made single-call tests pass. Fix pattern: capture `seg_base` at segment entry and compute in-segment windows from it. Probe technique: instrument `register_placed_markers` + both call sites, run a single-paragraph two-call fixture, compare printed windows against expected byte offsets (the 2× signature is unmistakable).
- **"Two wrongs matching" applies to footnote tests too (verified CORE-146):** CORE-107's suite covered same-page and per-page-paragraph cases only; the bug needed ONE paragraph with TWO calls whose lines land on DIFFERENT pages. When adding fixture coverage, include two markers in one spanning paragraph — a single-marker case can pass with the marker dropped entirely.
- **Demo corpus asset URLs resolve against the process CWD on main (verified CORE-146):** `--base-url` is parsed but not threaded into layout until CORE-140. build-demo.sh renders with `demo/corpus` as cwd so `assets/...` resolves identically for both engines. Fixtures with relative `url()`/`src` must ship assets under `demo/corpus/assets/` (font license files included).
- **Fragment offsets are PARENT-relative — shifting a subtree shifts only the top node (verified CORE-142):** shifting every node recursively (like the atomic-path `rebase_subtree`) COMPOUNDS at each nesting depth (+6pt per level). The atomic path gets away with it because those subtrees bake page-absolute coords internally; the block-path body tree does not. A body-margin shift is a single `fragment.offset.y += mt` at the root. Related: the emitter walks page.root accumulating offsets, so shifting the body fragment shifts all in-flow paint exactly once; abspos/footnote/margin-box attachments live OUTSIDE the body fragment and are unaffected.
- **A Text run's baseline is PARENT-relative — even in hand-written test walkers (verified CORE-150, 2026-09-08):** the PDF emitter rebases a Text run off the PARENT's absolute origin (pdf.rs: `x: parent_x + run.baseline.x`), NOT the fragment's own offset; a walker that adds both double-counts and puts baselines below the page bottom. Mirror the emitter's walk exactly (accumulate frag.offset for CHILDREN, rebase run.baseline off parent only).
- **Pre-existing engine residual (CORE-150):** `attach_footnotes` paints notes at a hardcoded 13.45pt pitch while `footnote_area_height` reserves the note style's own line-height — with notes <12pt the band under-reserves and notes overrun into the bottom margin on EVERY footnote page. Fix belongs with the footnotes seam, not multicol.
- **Zero-area background rects are fatal in krilla (verified CORE-139):** Rect::from_xywh fails on w<=0||h<=0 and pdf.rs aborted the whole render. Grid auto-tracks can size to 0 (empty cells) — pdf.rs now skips degenerate rects.
- **Check whether a failing test's REFERENCE declares the same trigger as the TEST before implementing a root-level feature** (verified CORE-181): `page-size-012` passes only because BOTH sides render horizontal text — its test declares the root `writing-mode`, while its reference has a HORIZONTAL root that simulates the vertical layout with inner `writing-mode: vertical-rl` divs. A trigger keyed on the ROOT element transposes one side and not the other, so a currently-PASSING pair breaks and only interior-feature support can repair it. Read both fixtures' declarations BEFORE the frame work, name each asymmetric pair on the issue, and ask the user before counting those pairs as classified flips. `page-margin-002/003` are the good canary pair: their references DO declare the root mode, so they should survive and prove the frame arithmetic.
- **An out-of-flow subtree cannot be exempted from a frame change locally** (verified CORE-181): an abspos box inside a vertical root is usually `horizontal-tb`, so relabelling the page axes turns its text vertical — it needs a PHYSICAL frame plus a paint-map exemption. But its containing block comes from `Ctx` (`flow.abspos_cb`) and it is laid out inside the parent's child-item loop, so a second `Ctx` must be threaded through the block path. Budget for that before starting a whole-page frame swap; it is the cost that made two prior CORE-181 attempts net-negative.
- **Relabelling the page frame does NOT relabel box dimensions** (verified CORE-181): swapping the page rect for a root-vertical document (virtual x = physical y, virtual y = physical x) makes the vertical fragmentation machinery slice along the physical x axis, and the page-chrome/abspos/ footnote paths keep the physical rect — but the TARGET page counts do not move at all, because every box still carries its physical `width`/`height` and the horizontal machinery reads `width` as the inline extent and `height` as the block extent. In a vertical writing mode that mapping is reversed, so `div { width:600px; height:100px }` gets a 600-wide inline extent inside a 600-wide virtual frame and a 100 block extent and can never cross a page edge. A frame swap needs a STYLE transpose in the same change (`width` ↔ `height` plus min/max and resolved `vw`/`vh`, then `margin`/`border`/`padding` side swaps). Probe it cheaply: transpose only the widths/heights of one fixture's boxes and re-measure that fixture's page count. Canary pairs prove the frame arithmetic separately — `page-margin-002/003` hold their 3/3 counts under a frame swap alone, so a canary flip means the frame math is wrong and an unmoved target means the STYLE transpose is missing.
- **Do NOT widen the CORE-153 inline-extent fill to `writing_mode_at`** (verified CORE-182, 2026-09-15): that rule means "the box fills its CONTAINING BLOCK's inline size". Under a vertical PAGE flow the fragmentainer is that containing block for the root/body chain, but an interior vertical box inside a horizontal flow has a content-based, indefinite containing-block inline extent. Keying the fill on the box's own mode grew an interior `vertical-rl` wrapper to 210pt of a 216pt page and pushed its second child onto a new page. It needs a definite containing-block inline size first (the engine models DECLARED extents only, `specified_extent`). Blocking guard: `engine/tests/page_boundaries.rs::page_change_suppressed_when_inner_mode_orthogonal_to_page_flow`. The ANCHORING half of the same rule IS safe to re-key: zero flips and spec-correct, because a horizontal block axis right-anchors.
- **A "did the box stretch?" assertion must filter by fragment CONTENT** (verified CORE-182): a `Line` fragment is created at the LINE-BOX width whatever its container's height, so a `width ≈ N && height < M` filter over all fragments matches a line rather than the container and the test passes without its fix. Walk only fragments carrying a paint (`FragmentContent::Background`).
- **`images::sniff` supports PNG, JPEG and SVG only — no GIF** (verified CORE-183): a GIF `data:` URI interns as `ImageEntry::Broken`, so it paints nothing even when the layout path is correct. Check the FORMAT before blaming the painting seam: render the same markup once with a PNG and once with the fixture's own bytes (`probe/control.py` in the core-183 worktree does this), which separates format from plumbing in a single run.
- **A reversible RED check inside the working tree needs EXACT anchors** (verified CORE-183): save `(fixed_text, pre_fix_text)` pairs to /tmp, revert with a count assert, run the tests, then restore with the mirror assert. Generic anchors bite — reverting `is_replaced_image` to a bare `        false` line matched two other lines on restore, and a `for decl in body.split(';') {` anchor matched four passes. Anchor on the enclosing function body, or patch by verified line index.
- **GIF support = TWO load-bearing seams, test both RED** (verified CORE-186, 2026-09-15): (1) `images::decode_data_uri` gates on MIME with `_ => None`, so an `image/gif` data URI never LOADED its bytes — `intern` fell back to hashing the URL TEXT, and sniffing alone would not have fixed the fixture; (2) `sniff` needs a GIF branch. Reverting seam 1 fails `gif_data_uri_loads_its_bytes`, reverting seam 2 fails the intern and layout tests — three of the four new tests RED, one helper test stays green (headers still parse).
- **GIF → PNG normalisation at intern time** (verified CORE-186): decode the FIRST frame with `gif::DecodeOptions::set_color_output(RGBA)` into a canvas sized at the LOGICAL SCREEN size (compose partial frames at their `left/top` offset), PREMULTIPLY alpha (tiny_skia pixmaps are premultiplied), then `resvg::tiny_skia::Pixmap::encode_png` — the same normalise-at-intern shape as the SVG bridge, so `ImageKind` stays `Png` and `pdf.rs` never changes. Added `gif = "0.13"` (pure Rust); decision recorded on the issue.
- **NEVER hand-type base64 constants in tests** (verified CORE-186): a single dropped character silently corrupts LZW — `is_gif` (first 6 bytes) still passes and the decode fails with a 0x0 result, so the failure message points at the code, not the constant. Generate the constant from the fixture programmatically (regex the data URI out, write it with `re.subn`, assert the exact length) — hardcoding by eye dropped one char (287 vs 288) and cost a false-red cycle.
- **Moving a fragment kind OUT of the content tree breaks every test helper that reached it through `root`** (verified CORE-179): taking margin boxes out of `Fragmentainer::root` (they are their own stacking contexts) failed 15 tests across FIVE files whose helpers walked `page.root` looking for them (CORE-178's baseline helper in `layout.rs`, plus paged_media, images, print_media_queries, tounicode). Fix shape: expose the ordering ONCE on the fragmentainer (`margin_boxes_in_paint_order()`, `paint_roots()`) and have emitter and tests both consume it. Before changing a tree shape, grep the test suite for the walker — and expect the suite to abort at the FIRST failing binary, so run `cargo test --no-fail-fast` to see all of them (43/43 green as of CORE-179).
- **The page-wide paint passes cannot express stacking order** (verified CORE-179): because the emitter collects ALL backgrounds, then ALL borders, then ALL text into separate vectors, a later sibling's background paints under an earlier sibling's text. Any box that must be painted as ONE stacking context (background → border → content) needs its own unit painter (`paint_margin_box()` is the pattern), not the global passes. Related layer trap: a page-anchored out-of-flow box attaches AFTER the in-flow content, so a NEGATIVE `z-index` still painted on top; CSS2.1 Appendix E requires attaching it BEFORE the content (insert at the front, in REVERSE so the negative run keeps ascending z-order).
