# Pagination, Fragmentation, and Absolute Positioning

Page breaks, drains, and abspos continuation lessons verified against real CORE issues. Read this before touching pagination, page counts, or out-of-flow layout.

## Lessons

- **The harness only prints page counts on MISMATCH — measure both sides** (verified CORE-155): `page count mismatch: test=N ref=M` never says which side is right, and a test can PASS at a count driven by a side effect rather than the feature under change (`page-name-orthogonal-writing-001` passes at 2-vs-2 pages because a root vertical mode makes each block fill the page's inline axis, NOT because of the page change; a unit test expecting 1 page there was wrong). To get both counts, render with the harness's own `CliEngine` + `harness.manifest.parse_test` and count pages with pypdfium2 (one fixture per line), rather than guessing from the failure message.
- **A drain that re-enqueues on `outgoing` must survive a MONOLITHIC layout path** (verified CORE-185): `layout_image` ignores break tokens — it returns an empty fragment plus `break_before` whenever a replaced element does not fit — so a deferred `content: url()` box regenerated its own token every page: 100_000 pages, the `MAX_PAGES` cap. The harness reported that as "worker crash: A process in the process pool was terminated abruptly", NOT as a page-count failure, so the symptom points at memory rather than pagination. Any new defer/re-enqueue path needs a non-progress guard: retry once as a LAST-RESORT placement (the empty-page rule `layout_image` itself uses) and drop the job if it still refuses. Diagnose by counting pages ONLY (`len(pdf)` + `get_size()`) — RASTERISING such a PDF hangs, which reads as a hang in the probe rather than a bug in the engine.
- **The Chromium oracle settles a forced break at document end: NO trailing page (verified CORE-176):** the issue's diagnostic-step-2 assumption ("a trailing `break-after: page` demands a blank final page — Chromium produces one") was WRONG; Chromium renders `<div style="break-after: page">one</div>` as ONE page (basic-pagination-001 codifies it). The used value of a forced break at the end of the document produces no page, so the blank-page drop needs no forced-break exception — the forced break-after handler only fires when a NEXT item exists, which is already correct. Verify oracle claims quoted in a ticket against the oracle before encoding them in a predicate.
- **Count skipped extent toward declared height at a break** — and fix it at TOKEN EMISSION, not at the break site (verified CORE-152, 2026-09-13): a forced child break inside a declared-height parent consumed zero progress, re-rendering the skipped space as extra pages (5 vs Chromium 4). The fix is one hunk where the BreakToken is built: when `broke` and `style.height.is_some()`, advance `consumed_block_size` to `max(box_height, bottom_limit - box_top)`. Don't touch the six per-child `broke` sites — they only defer children; progress accounting lives in one place. Scope to declared-height boxes (without `height` no block-path reader consumes the token, so no other bucket shifts) and require `box_height > 0` (zero-height fragments must not emit progress or the page loop can spin).
- **Extent-occupies-flow must compose with CORE-152's continuation machinery (verified CORE-167, 2026-09-13):** a rebase onto a release tip that gained `height_continues`/`declared_extent` code silently DELETES those tests' support if you resolve conflicts by taking only your side — 5 fragmentation tests fail with `height_continuation_*` names. The compose: `remaining_spec` (extent minus `consumed_block_size`) drives the slice; `height_continues` is not re-added, but the seen-all early-out, the paint box, and the extent slice all read the same `specified_extent()` helper. Also: CORE-152's `height_continuation_forced_child_consumes_extent` requires broken declared-height boxes to consume skipped room (max(room, box_height)) per css-break-3 §5.3 — plain `box_height` consumption fails it.
- **A declared-height box that crosses the page edge can flip tests whose baseline pass was "wrong in a matching way" (verified CORE-167):** page-margin-auto (flex item measure grew → auto-margin centering shifted), column-balancing-paged-001 (multicol measure path), fixedpos-with-abspos-with-link (body 250vh now spans pages). When the A/B flags ~2-3 such flips all declaring `height`, classify against css-standards-alignment and document as newly-exposed gaps rather than reverting the feature — but re-run the FULL A/B after every reconciliation, never trust a gate run against a stale binary.
- **Page-anchored abspos drains need a job queue + keepalive token (verified CORE-169, 2026-09-13):** fragmenting abspos across pages needs THREE coupled pieces — (1) defer whole via an `AbsposJob` queue + forced break, (2) drain the page-start snapshot through `layout_table_like` (NOT `layout_box` — flex/grid abspos containers take their own paths) with a real `bottom_limit`, pushing fragments DIRECTLY to the fragmentainer root, (3) the body item loop must skip drain-owned children (carry their token with `broke=true` while jobs exist, drop when finished) AND the page loop needs a keepalive token (`seen_all=true`, NOT `break_before` — that would reset the named-page context via `PageCtx::Reset`) when the body token is None but jobs remain. Without the keepalive the last abspos fragments vanish; without the carry-arm `broke` the loop terminates early; without the finished-drop a blank trailing page appears.
- **page-margin-004 renders EMPTY post-CORE-169 (verified CORE-153, 2026-09-13):** an abspos box containing a `break-before:page` child paints NOTHING (1 page, COL none) where pre-169 it painted the yellow box on page 1. CORE-169's page-anchored-abspos drain drops it; the failure message stays "page count mismatch: test=1 ref=2" both before and after, so the status-only A/B gates never saw it. Suspect the same shape whenever an abspos with an explicit forced break inside goes missing — probe CONTENT, not just status.
- **A page-anchored abspos that breaks inside needs a REAL bottom limit and a drain enqueue, not the monolithic model (fixed 34c57bb, CORE-153, 2026-09-14):** the direct placement path laid page-anchored boxes (auto insets, no positioned ancestor) against `bottom_limit = f64::MAX` (spec Behavior 9 "monolithic"). Two compounding bugs: (1) a forced child break or declared-height overflow returned an outgoing token the branch DROPPED — the continuation never rendered; (2) fill-to-edge computed `paint_height = bottom_limit - box_top = f64::MAX`, and pdf.rs drops the huge rects (f32 overflow), so the box painted NOTHING (one thin top slice of border+text at most). Fix: page-anchored boxes lay against the REAL fragmentainer bottom; on outgoing, enqueue `AbsposJob` + resume token. Keep the f64::MAX monolithic model for PINNED boxes only (any inset or positioned ancestor — fixedpos-010, page-name-abspos-002 rely on it).
- **The abspos continuation must NOT carry a body token — the keepalive drives drain-only pages (verified CORE-153, 2026-09-14):** the drain runs AFTER the body on each page. If the placement-continuation branch also does `broke=true; outgoing_children.push(deferred)`, the next body sees the fresh resume token and keeps paging past the drain's final page — a trailing BLANK page (test=3 vs ref=2). Carry nothing: with no in-flow content after the box, the keepalive (incoming None + jobs non-empty → `seen_all` token) produces the drain-only page; a later body with REAL content skips the box via a drain-owns-it guard (pending job OR resume token) before placement. This mirrors the deferred path: a deferred box gets NO resume token until the drain re-enqueues (after that page's body), so its body never carries either.
- **Abspos pagination flips fixedpos-001/002 — exposed accidental passes (verified CORE-153, 2026-09-14):** after the 004 fix, fixedpos-001/002 flip PASS→FAIL — CLASSIFY before reverting. The ref renders 1 page while Chromium's test needs 3 (the pinned inset-abspos model, `bottom: -100vh`, never advances the page loop); the old PASS was "wrong in a matching way" (our test laid its 300vh abspos monolithically, matching the ref's 1). Verify with the oracle (Chromium passes fixedpos-001/002 at 3 pages) and apply the CORE-140 ruling — land spec-correct, document the flip as an exposed ref-pagination gap.
- **The harness only prints page counts on MISMATCH, so measure both sides** with a direct probe when tuning pagination (verified CORE-181): render each fixture with the CLI at the harness geometry (`--page-width 5in --page-height 3in` plus the four 0.5in margins) and count PDF pages with pypdfium2. Watch the ref naming: `css-page/` refs are `<name>-ref.html` while `css-break/` print tests use `<name minus -print>-ref.html`, so try both candidates. Note that a ref which itself declares the root writing mode moves WITH the test side (CORE-181 measured `block-001/002-wm` refs changing too) — only a horizontal ref is a stable baseline.
- **A CLIPPING ancestor suppresses abspos pagination — and the engine had no `overflow` model at all** (verified CORE-187): `abspos-in-clipped-overflow-print` (a `height:350vh` abspos child of an `overflow:clip` box) is ONE page in Chromium and its own fixture text says so, yet handing pinned boxes a real bottom limit paginated it (PASS→FAIL). The seam added: `ComputedStyle.clips_overflow` + `Ctx::clips_overflow_ancestor`. Find a property's computed type and owning struct BEFORE guessing an accessor: `awk "/^\[property-name\]/,/^\[/" /cargo-home/registry/src/index.crates.io-*/stylo-0.20.0/properties/longhands.toml` (overflow-x/y → `type = "Overflow"`, `struct = "box"` → `box_.clone_overflow_x()`, reachable as `style::values::computed::box_::Overflow`).
- **The pinned abspos drain runs AFTER the body, so a body-pushed continuation must wait one page** (verified CORE-187): a job pushed with `target: Some((x, y))` whose target page IS the current page is consumed by the SAME page's drain and paints the continuation over the fragment just placed. The job carries `defer_one_page` (set only by the CORE-187 continuation; every other construction site passes `false`) and the pinned loop re-queues it once.
- **The pinned drain's `ty` is ALREADY page-local** (verified CORE-187): use `local_top = ty - target*content.height`, NOT `ty - (content.y + target*content.height)`; the extra `content.y` moved fixedpos-004's ref side 0.5in up. Same loop: a job that FITS one fragmentainer must lay with `f64::MAX` (overflow in place, like Chromium's abspos overflow) — with a real bottom limit it fragments into extra pages exactly when the pair nearly matches.
- **A monolithic parent leaks its `f64::MAX` bottom limit to nested abspos children** (verified CORE-204, 2026-09-18): a child laid inside an abspos parent that FITS one page inherits the parent's `box_bottom_limit = f64::MAX`, so `y + fh > bottom_limit` can never fire and the CORE-187 fragmentation path never runs (overflowing-block-print-ref rendered 1 page vs Chromium's 3). Fix shape: decide every out-of-flow fragment decision against the REAL fragmentainer bottom `content_y + page_height`, never the inherited limit; the two coincide at the body level, so only the nested path changes. Also: `resolved_height` ignores PERCENTAGE heights (they live on `height_percent`, consumed only by the `resolved_height_or_percent` walk) — the pinned-fragmentation declared-extent test MUST use the CORE-169 walk or `height:300%` stays monolithic (toplevel300 probe: 1 page vs Chromium's 3).
- **A percentage-height abspos fixture must keep html/body STATIC or the chain is indefinite** (verified CORE-204, 2026-09-19): my first RED fixture used `* { position: absolute }` with no declared heights — html/body go auto-height, so the child's `height: 300%` resolves against an INDEFINITE ancestor chain and Chromium renders it as ONE page (my test wrongly wanted 3). The engine was right; the fixture was wrong. Oracle-verify the exact fixture shape (html/body static vs absolute, margins 0 and 0.5) before asserting a page count in a unit test.
